## Goal

Get `com.ticitacatoey` into the App Store and Play Store, with the mobile
app at feature parity with the web where parity actually matters, and
without shipping the one credential in the system generated by
`Math.random()`.

## Where things actually stand

Better than feared. **Protocol parity is exact**: every message type the
web sends, mobile sends, except `CURSOR` - which mobile deliberately
never sends because a finger has no hover. Every game feature is there:
variants, teams, timers, forfeit, open seats, spectator upgrade,
leaderboard, player profiles, replays with the seat legend, history,
handle claiming, deep links, move bursts, and cursor ghosts.

The drift is not in the game. It is in the shell around it - legal
links, version, help depth - plus a set of things that were never needed
until we decided to ship to a store.

Verified 2026-08-07: production is live on v1.10.0, `/privacy.html` and
`/terms.html` serve correctly, and the mobile source compiles clean
(`bun run typecheck`, both metro bundles).

## Blockers

### B1. The playerKey is not random (security) - DONE 2026-08-07

`mobile/src/state.ts:383` builds the only credential in the system from
`Math.random()`:

```ts
playerKey = `m-${Date.now().toString(36)}-${Math.random()...}`;
```

The web uses `crypto.randomUUID()`. `Math.random()` is not a CSPRNG and
the timestamp prefix leaks when the key was made, so the search space is
far smaller than it looks. Whoever holds a playerKey *is* that player -
their handle, their rating, their history. This is fine while the app is
unpublished and has no real users; it is not fine the day it does.

React Native 0.86 has no `crypto.getRandomValues` (checked - not in RN's
Libraries, types, or ReactCommon).

**Recommendation: let the server mint it.** Zero new dependencies (the
house rule), and the server already has real crypto plus the
key-hash -> playerId table. A client that registers *without* a key gets
one minted with `crypto.randomUUID()` and returned in its own
`REGISTER_PLAYER` response, which already goes only to that one
connection. The client persists it. Web keeps generating its own and is
untouched. No migration needed - mobile has no published users yet.

The alternative, `react-native-get-random-values`, is one small
dependency but needs an explicit exception to the approved-deps rule,
and only fixes the phone.

### B2. Nothing legal in the app - DONE 2026-08-07

Both stores require a privacy policy, and Apple expects it reachable
from inside the app. Mobile currently has **no** privacy link, no terms
link, and no version string anywhere. The web footer has all three.

We already serve `/privacy.html` and `/terms.html`, so this is a link,
not new content.

### B3. Versions are stuck at 1.0 - DONE 2026-08-07

`versionCode 1` / `versionName "1.0"` (Android) and `MARKETING_VERSION
1.0` / `CURRENT_PROJECT_VERSION 1` (iOS), while the project is on
v1.10.0. Needs a scheme - see Decisions.

### B4. Android release builds are signed with the debug key

`mobile/android/app/build.gradle:103` still has the React Native
template's `signingConfig signingConfigs.debug` under `release`, with
the comment warning not to ship it. Play will reject a debug-signed
upload. **A release keystore does not exist yet.**

This one is yours: a keystore is a credential, so I should not generate,
hold, or commit it. Create it, store it somewhere safe and backed up
(losing it means never updating the app again), and put its passwords in
`~/.gradle/gradle.properties`, never in the repo.

### B5. iOS signing is Developer, not Distribution

`CODE_SIGN_IDENTITY[sdk=iphoneos*] = "iPhone Developer"`. Archiving for
the store needs a Distribution certificate and provisioning profile -
done in Xcode against your Apple Developer account. Also yours.

### B6. The iOS toolchain on this Mac cannot build at all right now - RESOLVED (see checkpoint)

Not a code problem - I proved the source is fine by other means, but
every `xcodebuild` invocation fails with *"Found no destinations for the
scheme"*. Diagnosis:

- `xcode-select` points at **Xcode 26.6**, whose SDK is iOS 26.5.
- The only simulator runtimes installed are **iOS 27.0**, which belong
  to **Xcode-beta 27.0**, also installed.
- No runtime matches the selected Xcode, so zero destinations resolve.
  The physical iPhone is ineligible for the same reason ("iOS 26.5 is
  not installed").

Two paths, and they are for different purposes:

- **To develop and test today**, prefix builds with
  `DEVELOPER_DIR=/Applications/Xcode-beta.app/Contents/Developer`. No
  sudo, no system change. Verified: all simulator destinations resolve.
- **To submit**, Apple requires a *released* Xcode - a beta archive is
  rejected. So Xcode 26.6 needs its iOS platform component installed
  via **Xcode > Settings > Components**. Multi-GB download, your
  machine, your call on timing. Do this early; it is the long pole.

### B7. The app has never run on a device or emulator - DONE (both)

`TODO.md` has carried "Android emulator/device pass" as pending since
before launch. We have shipped ten server releases without once seeing
the mobile app run. The Android SDK is installed here and iOS
simulators work via B6's workaround, so this is now doable - it just has
to actually happen before we submit.

## Important, though not strictly blocking

### I1. Universal Links and App Links are dead - iOS DONE, Android blocked on B4

`https://ticitacatoey.com/.well-known/assetlinks.json` and
`/.well-known/apple-app-site-association` both return **the SPA fallback
HTML** with `content-type: text/html` (checked today). The Android
manifest already declares `android:autoVerify="true"` for the domain, so
verification is silently failing, and iOS has no Associated Domains
entitlement at all.

This matters more than it sounds. The invite loop *is* sharing a link.
Today a shared `https://ticitacatoey.com/play/<id>` opens the browser
even for someone with the app installed. The custom scheme
(`ticitacatoey://`) works, but nothing generates those links.

Note `assetlinks.json` needs the release keystore's SHA-256, so it is
blocked on B4. The AASA file only needs the Team ID (`NZ2N94X98Y`) and
bundle id, so it can be done now. Both must be served with real JSON
content types - `static.ts` will need an explicit case, since the SPA
fallback currently swallows them.

### I2. Parity polish - help DONE

- **Help**: web's is 127 lines and was deliberately expanded; mobile's
  is one paragraph in a modal. First-run experience on a phone is the
  one that most needs it.
- **Timed games**: web offers an increment picker, mobile hardcodes
  `1000`.
- **Version display**: fold into B2's footer.

Not a gap, despite looking like one: **mobile has no QR invite**. It
uses the native share sheet, which is the right idiom on a phone - the
QR exists on web so a laptop screen can be scanned *by* a phone.

## Decisions (resolved 2026-08-07)

1. **Version scheme: the mobile app carries the repo tag it ships from.**
   So "what version is this?" has one answer across `/health`, the web
   footer, and the phone. First submission goes out as **v1.11.0**.
   Build numbers (`CURRENT_PROJECT_VERSION`, `versionCode`) stay
   monotonic integers independent of the tag, since stores require that.
2. **Both stores simultaneously.** This makes B6 (the Xcode platform
   component download) the gating item for the whole launch - it is the
   one thing with a hard, unskippable lead time. Everything else runs in
   parallel with it.
3. **Scope of I2:** help parity is in; the increment picker can wait.

  Symbol or a bitmap and SF Symbols do not exist on Android.

  They are generated, not drawn: `mobile/scripts/make-tab-icons.ts`
  holds the five shapes as geometry and rasterises them with
  supersampled anti-aliasing to `src/icons/tabs/*.png` at @1x/@2x/@3x,
  zero dependencies (the PNG encoder is in the script; only `node:zlib`
  is imported). So the artwork stays editable and diffable rather than

  colour in the file, because the bar supplies it: iOS tints for
  selected/unselected on its own, Android via `tintColor`.

  What it buys back: the app no longer has two icon sets to keep in
  step, and `sf-symbols-typescript` - a package we imported without ever
  declaring it - is out of the code entirely.
